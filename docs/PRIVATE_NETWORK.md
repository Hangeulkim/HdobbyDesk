# 직접 연결과 내부 서버 설정

이 수정본은 공개 ID·중계 서버를 기본값으로 선택하지 않는다. 내부 서버 주소와 키를 소스에 넣지 않으며, 운영자는 자신의 설정을 각 기기에 직접 입력한다. Windows 호스트에 실물 Android와 Mac 컨트롤러가 직접 연결되는 경로는 확인했지만 전체 플랫폼·장시간 시험을 마친 릴리스는 아니다.

| 설정 | 비어 있을 때 | 지정했을 때 |
|---|---|---|
| ID 서버 | 등록·ID 조회를 위한 기본 서버 없음 | 지정된 서버만 사용; 과거 응답에 저장된 서버 목록 무시 |
| 중계 서버 | 중계 연결 거부 | 각 기기에 지정한 호스트·포트와 일치하는 중계만 허용 |
| API 서버 | 계정·관리 API 기본 서버 없음 | 명시한 API 사용; ID 서버 주소에서 자동 추정하지 않음 |
| `custom-stun-server` | IPv4·IPv6 STUN 조회 생략 | 명시한 STUN만 조회; 현재 별도 UI 입력란은 없음 |
| WebRTC ICE 서버 | 호스트 후보만 사용 | 명시한 ICE 설정 사용; 기본 STUN 추가 없음 |

공개 업데이트 서비스와 외부 DNS 서비스를 이용한 NAT64 주소 변환도 제거했다. IPv6 전용 환경에서 IPv4만 있는 상대 기기는 연결에 실패할 수 있으며, 운영자가 직접 접근 가능한 주소를 준비해야 한다. 중계 주소가 다르면 서버가 광고한 주소를 자동으로 신뢰하지 않는다. 별칭이나 IP와 호스트 이름을 섞기보다 양쪽에 같은 중계 주소를 입력한다.

원본의 직접 IP 연결 경로는 암호화된 전송으로 취급할 수 없다. 현재 수정 소스는 해당 경로를 TLS 1.3으로 바꾸고 등록한 인증서가 없으면 연결을 거부한다. 실물 Android에서 이동통신망을 통해 Windows 호스트의 화면과 터치 입력까지 확인했다. 전체 앱의 외부 통신 차단, 사용자가 지정한 ID·중계 경로, 장시간 트래픽과 구현 전체의 암호학적 검토는 별도 미완료 항목이다.

## 직접 TLS 개발 상태

직접 연결은 사용자 입력 주소로 TCP를 만들고, 그 위에서 rustls의 TLS 1.3을 사용한다. 기존 프록시·ID·중계·STUN 설정을 조회하지 않는다. 주소가 도메인이면 운영체제의 DNS 해석은 필요하다. 같은 로컬 네트워크의 IP나 사용자가 준비한 직접 도달 가능한 주소가 필요하며, TLS가 NAT나 방화벽을 자동으로 통과시키지는 않는다.

호스트는 비공개 런타임 파일에서 인증서·개인키를 읽는다. 홈 화면의 직접 연결 준비에서 인증서 준비 버튼을 누르면 로컬 앱 저장소에 인증서와 개인키를 생성한다. 기존 파일이 있으면 재사용하고 손상된 파일을 자동으로 덮어쓰지 않는다. 파일이 없거나 잘못되면 수신 포트를 열지 않는다. Unix의 새 파일 권한은 0600이다. 설치형 Windows는 `%ProgramData%\\HdobbyDesk\\identity`의 기기 전용 파일을 사용하고 LocalSystem과 Administrators만 접근하는 ACL을 적용한다. 이전 설치가 읽을 수 없는 ACL을 남겼을 때 서비스가 파일을 열기 전에 고정 정책을 다시 적용하도록 수정했다. 실제 설치 서비스에서 기존 인증서와 비밀번호를 보존한 채 두 차례 재시작 후 `listening` 상태를 확인했다.

수신 인터페이스는 선택 옵션 `direct-listen-ip`로 한정할 수 있다. 비어 있으면 기존 전체 인터페이스 수신을 유지하며, 지정할 때는 해당 기기에 실제로 할당된 IPv4·IPv6 주소만 사용한다. 호스트 이름이나 `IP:포트` 형식은 받지 않는다. 로컬 시험은 루프백 IP를 명시한다. `direct-access-port`가 비어 있으면 21118을 사용하고, 지정한 값이 1–65535를 벗어나거나 IP가 잘못되면 수신을 중단한다. 잘못된 값으로 전체 인터페이스나 다른 포트에 대신 바인딩하지 않는다. IP·포트 선택을 바꾸면 기존 수신 소켓을 닫고 다시 연다. 이 선택 옵션의 별도 UI는 아직 없다.

컨트롤러의 기기별 `direct-tls-trusted-cert` 옵션에는 호스트가 표시한 공개 인증서의 `hdobby2:` 페어링 코드를 등록한다. 코드는 신뢰하는 별도 경로로 전달하며, 접속한 상대에게서 자동으로 받아 신뢰하지 않는다. 이 코드는 개인키나 로그인 비밀번호가 아니지만 운영 정보이므로 Git에는 포함하지 않는다. 직접 연결 준비 UI에서 상대 주소와 코드를 입력하고 지문을 확인한 뒤 명시적으로 등록한다. 교체 시 기존 지문도 표시하고 저장 직전의 변경 여부를 검사한다. 입력을 바꾸면 이전 확인이 취소되고, 저장 결과를 확인할 수 없으면 성공으로 표시하지 않는다. iPhone·발신 전용 구성에는 호스트 인증서 생성 UI를 표시하지 않는다.

신뢰 저장소에는 등록한 인증서 하나만 넣는다. 공개/OS 인증기관 저장소, 검증 실패 우회, 평문 전환, 0-RTT와 세션 재개를 사용하지 않는다. 인증서 유효기간·프로토콜 이름·서명을 검증하고, 최종 상대 인증서가 등록한 인증서와 같은지 확인한 뒤 앱 메시지를 허용한다. 호스트의 사용자 접근 승인은 이후 기존 비밀번호·승인 절차가 담당한다. `hdobby.direct`는 인증서 안의 고정된 프로토콜 이름이며 외부 서버 주소가 아니다.

직접 TLS는 양쪽에 수정본과 페어링이 필요하다. 원본 RustDesk의 평문 직접 접속과 호환되지 않는다. TLS 핸드셰이크는 기존 연결 제한 시간 안에서 종료하고, 호스트의 동시 핸드셰이크를 16개로 제한한다. 사용자가 지정한 내부 ID·중계 경로는 별도의 기존 프로토콜이며 이 TLS 시험의 통과 범위에 포함하지 않는다.

ID 서버를 사용하는 경로에서는 서버 키가 없거나 서명·상대 ID가 일치하지 않으면 연결을 중단한다. 호스트도 빈 키 교환 메시지나 잘못된 메시지를 받으면 중단한다. 원본의 비암호화 전환 동작을 허용하지 않는다. 설정이 비어 있는 상태도 공개 서버 사용 상태로 표시하지 않는다.

## 소스 준비와 로컬 검사

`hbb_common`은 Git 하위 모듈이다. 사용자 지시에 따라 하위 모듈에도 아직 커밋하지 않았으며 변경 내용은 검토 가능한 패치로 보존했다. 하위 모듈의 기준 버전을 준비한 뒤 저장소 루트에서 실행한다. 아래 스크립트는 다운로드·서버 연결·커밋을 하지 않는다.

```sh
python3 scripts/apply_private_network.py --apply
python3 scripts/test_private_network.py
cargo check --offline --locked -p hbb_common --lib
```

패치를 적용하지 않으면 앱에서 사용하는 정책 모듈이 없어 컴파일이 실패한다. 원본 하위 모듈로 조용히 되돌아가 빌드되는 경로를 두지 않는다. 패치 적용기는 기준 커밋과 적용 가능 여부를 확인하고 충돌이 있으면 변경하지 않는다.

로컬 정책 테스트는 운영 설정을 읽거나 DNS·TCP·UDP를 사용하지 않는다. 공통 라이브러리 전체 테스트에는 원본의 별도 개발 의존성과 테스트가 있으므로 이 명령의 통과를 전체 앱 시험으로 해석하지 않는다. 서버가 필요한 실기기 시험은 [시험 조건](PRIVATE_TESTING.md)에 따라 별도로 실행한다.

## 네이티브 전송 검증

Mac ARM64에서 `flutter,hwcodec,unix-file-copy-paste` 구성을 오프라인으로 컴파일 검사했다. 원본에 고정된 vcpkg 코덱과 NASM 2.16.03, pkgconf 2.5.1을 사용했다. `screencapturekit` 시스템 오디오 구성은 `cidre`가 전체 Xcode를 요구하여 미완료이며, 이를 기본 코어 검사로 대체 통과 처리하지 않는다.

```sh
# Mac 빌드 의존성과 원본 Flutter 브리지를 준비한 환경에서 실행
cargo check --offline --locked --features flutter,hwcodec,unix-file-copy-paste --lib
cargo test --offline --locked --features flutter,hwcodec,unix-file-copy-paste \
  --lib hdobby_ -- --test-threads=1
```

전송·수신 설정 테스트 17개는 루프백의 임시 포트, 메모리에서 생성한 키와 임시 디렉터리만 사용한다. 기존 클라이언트·호스트 키 교환 5개와 직접 TLS 및 수신 설정 12개가 통과했다. 직접 TLS에서 정상 왕복과 양방향 암호문, 지정된 엔드포인트로 연결, 잘못된 인증서·만료·이름 불일치·잘못된 개인키 거부, 평문 거부, 시간 제한, 저장 파일의 덮어쓰기 거절과 손상 거부, raw 모드의 TLS 유지와 연결 종료, 주소 검증, 기존 인증서 재사용, 잘못된 수신 IP·포트 거부를 확인했다. 운영 설정이나 사용자 문서는 읽지 않는다. 이는 원격 화면·입력·연결 안정성 실측이나 전체 암호 프로토콜의 보안 감사를 의미하지 않는다.

현재 TLS 소스의 Mac ARM64 릴리스 코어·서비스 helper·Flutter App.framework, Android ARM64 코어·APK, Windows x64 코어를 빌드했다. Windows 최종 코어는 설치 서비스에 배포해 연속 재시작 뒤 수신 상태와 Mac에서의 직접 TCP 도달을 확인했다. 실물 Android 2092에서는 저장된 인증서와 영구 비밀번호를 재사용해 Windows에 직접 연결하고 화면·터치 입력·자동 가로 전환을 확인했다. Mac v35에서는 저장된 인증서·영구 비밀번호·Console 세션을 재사용해 완전 종료 후 추가 입력 없이 실제 Windows Console 화면까지 연결됐고, v34 연결의 30분 관찰에서도 단절이 없었다. Android 2094는 Android 14 이상에서 승인 즉시 가상 화면을 만들고 이후 연결마다 표면만 교체하도록 수정했으며 API 36 가상 기기에서 지연 연결·강제 종료·재연결 동안 승인창 재표시 없이 캡처가 재개됐다. Android 2095는 iOS 텍스트·PNG 클립보드용 공용 Rust 브리지를 포함했고, 2096은 Windows의 현재 물리/별도 세션 표시를 추가했다. 2096 ARM64 APK는 빌드·서명·검사와 Lint 오류 0개를 통과했다. 2094~2096 실물 Android 호스트 시험, 전체 Xcode 빌드·공증된 배포 패키지와 iOS 실기기 시험은 미완료다.

Mac v40과 Android 2097 최신 후보에는 Windows의 Console을 `물리 모니터와 같은 화면`, RDP를 `별도의 Windows 바탕 화면`으로 표시하는 선택 정책을 넣었다. 저장된 RDP와 Console이 함께 있으면 Console이 기본 선택이며 RDP를 자동 재사용하지 않는다. Windows v41 코어는 현재 세션 범위를 보고하고, `RDP 별도 바탕 화면 제어`를 명시적으로 켠 경우에만 RDP 세션에 붙는다. 설정이 없거나 비어 있으면 물리 Console을 사용한다. 새 호스트가 세션 값을 제공하면 연결 메뉴에서도 물리 모니터/별도 바탕 화면 상태와 해결 방법을 표시한다. RDP 화면과 실제 모니터는 Windows의 서로 다른 세션이므로 같은 내용을 동시에 표시하는 것으로 설명하지 않는다. 기존 직접 연결과 Mac v40 재연결은 확인했지만 Windows v41을 설치한 실기기 조합은 아직 확인하지 못했다.

Mac v38과 v39는 각각 당시 최신 Flutter App.framework, Rust 코어와 서비스를 작업 폴더의 독립 후보로 패키징했다. v39는 Windows 세션 상태 메뉴까지 포함한다. ARM64 구조, 로컬 ad-hoc 서명, 전체 번들 서명, 공개 서비스 주소 0건, 운영 endpoint·인증정보 0건, 외부 동적 라이브러리·비이식 rpath·그룹/전체 쓰기 파일 0건을 검사했다. 설치·실행·네트워크 연결은 하지 않았으므로 v38·v39의 실기기 동작 증거로 사용하지 않는다.

수정한 Mac 실행 파일의 `--server` 모드에서도 루프백 수신을 시험했다. 등록한 호스트 인증서를 검증하는 TLS 1.3 클라이언트가 실제 앱의 로그인 전 인증 메시지를 받았다. 신뢰 인증서가 없는 클라이언트는 인증서 검증에서 실패했고 평문 접속은 거부됐다. 인증서 파일 누락, 잘못된 수신 IP, 서비스 중지 상태에서는 시험한 포트가 닫혀 있었다. 시험 후 프로필을 바이트 단위로 복원했고 인증서 파일 불변과 포트 종료를 확인했다. 이 실행에는 원격 로그인·화면·입력이 포함되지 않는다.

Android 16 ARM64 AOSP 에뮬레이터에서는 APK의 실제 기동·화면 표시, 인증서 준비, 복사·붙여넣기, 확인 전 등록 차단, 저장, 잘못된 코드 거부와 재시작을 시험했다. 첫 접속 전 인증서 등록이 재시작 후 사라지는 결함을 발견해 수정했고, 재시작 뒤 이전 지문과 교체 경고가 유지되는 것을 확인했다. 이어 실물 Android에서 Windows 직접 연결과 터치 입력을 확인했다. 에뮬레이터와 한 번의 실기기 세션은 장시간 안정성·모든 제조사·Android 호스트 검증을 대신하지 않는다.

입력·직접 연결 UI 패키지의 로컬 테스트 53개가 통과했다. 등록 전 지문 확인, 교체·실패·시간 제한·늦은 응답 무시, 재연결 제한, Windows Console/RDP 선택과 호스트가 보고한 현재 세션 범위, 좁은 화면과 큰 글꼴을 검사한다. 인증서 코드 붙여넣기는 버튼을 누를 때만 클립보드를 읽고 기존 지문 확인을 취소한다. 코드가 아닌 내용이면 입력을 덮어쓰지 않으며 자동 등록하지 않는다. 상위 앱의 입력 수정키·최근 연결·브랜드·설정·iOS 클립보드 집중 시험 24개도 별도로 통과했다.
