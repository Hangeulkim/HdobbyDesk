# 로컬 테스트와 서버 정보 관리

사용자 지시에 따라 Windows·Android·MacBook 실기기 테스트가 끝나기 전에는 커밋하지 않는다. 빌드·단위 테스트 통과만으로 실기기 테스트를 완료 처리하지 않는다. iPhone은 기기가 없어 미검증으로 남기며 커밋 전 필수 기기 시험에서는 제외한다. 이 조건이 충족되어도 서버 정보나 인증값을 Git에 포함하지 않는다.

사용자는 iPad 준비가 간단히 가능하면 진행하고 복잡하면 보류하도록 판단을 맡겼다. 자동 설치 경로를 확인했으나 이 Mac에는 전체 Xcode와 공식 iPhoneOS SDK가 없고, 개발 서명 계정·인증서·프로파일도 준비되지 않아 iPad 시험은 현재 보류한다. 우선 검증 대상은 Windows·MacBook·Android이다. iOS 컨트롤러의 텍스트·PNG 클립보드 경로는 구현하고 단위 시험과 Swift 구문 검사를 통과했지만 전체 iOS 빌드와 실기기 동작은 미검증으로 남긴다. iPad 호스트 기능을 지원한다고 표시하지 않는다. iOS 시험을 재개할 때 팀 ID·서명·기기 식별자는 저장소에 넣지 않는다.

## 원본 컴퓨터의 화면·입력 유지

Windows에 Console과 RDP 세션이 함께 있으면 물리 모니터와 같은 Console을 기본 선택한다. 선택 창은 `Console · 물리 모니터와 같은 화면`과 `RDP · 별도의 Windows 바탕 화면`을 구분해 표시한다. 저장된 Console은 다음 연결에서 자동 재사용하지만, 저장된 RDP와 Console이 함께 있으면 RDP를 조용히 재사용하지 않고 다시 선택하게 한다. RDP만 존재할 때는 무인 재연결을 위해 저장된 RDP를 재사용한다. RDP를 고르면 물리 모니터와 내용이 달라지는 것이 정상이며, RDP와 Console을 같은 바탕 화면으로 동시에 표시할 수 있다고 안내하지 않는다. 실제 모니터 동기화가 필요하면 RDP를 종료하고 Console로 다시 연결한다. 이 선택 정책의 단위 시험은 통과했지만 최신 UI의 실물 Windows 세션 선택은 아직 재검증하지 않았다. 이전 세션의 프라이버시 모드나 가상 모니터 요청은 연결 시 자동 복원하지 않는다. 해당 기능은 현재 세션에서 사용자가 직접 선택할 때만 요청한다.

Windows 호스트 설정의 `RDP 별도 바탕 화면 제어`는 기본으로 꺼져 있다. 끈 상태에서는 물리 Console을 제어하고, 사용자가 켠 상태에서만 Windows 원격 데스크톱이 만든 별도 바탕 화면을 제어한다. 구버전의 빈 설정값은 켜짐으로 해석됐지만 v41부터는 꺼짐으로 해석한다. 이 변경은 최신 v42 코어 빌드에도 포함됐으며 실제 Windows 서비스 배포 후 검증은 남아 있다.

새 Windows 호스트는 현재 실행 세션을 `physical_console`, `separate_desktop`, `unknown` 중 하나로 보고한다. 컨트롤러는 알려진 두 상태만 원격 메뉴에 표시하며, 분리된 화면이면 RDP 종료와 Console 재연결 방법을 안내한다. 알 수 없는 값과 이 필드가 없는 구버전 호스트는 추측하지 않는다. 파서의 정상·미래 값·누락 값 시험과 Windows x64 교차 빌드는 통과했지만 Windows 호스트 실행과 Mac·Android 실기기 UI 표시는 미검증이다.

실기기 시험은 다음 상태마다 원본 모니터의 실제 표시와 로컬 키보드·마우스 반응, 화면 수·주 모니터·해상도, 눌린 키·버튼 잔류를 확인한다. 화면 캡처나 디스플레이 목록만 정상인 것은 실제 모니터 정상의 증거가 아니다.

1. 연결 전 기준 상태와 연결 중 로컬·원격 입력.
2. 정상 연결 종료 뒤 원본 화면·입력 복귀.
3. 시험용 클라이언트 강제 종료와 시험용 연결 단절 뒤 복귀. 사용자 네트워크나 다른 원격 프로그램은 끊지 않는다.
4. 재연결과 반복 종료 3회, 마지막 원격 키/마우스 누름 직후 단절.
5. 명시적으로 선택한 프라이버시/가상 화면 시험은 별도 실행한다. 물리 모니터·드라이버를 바꾸므로 현재 화면을 사용 중일 때 자동 실행하지 않는다.

원격 호스트가 강제 종료된 경우의 복구와 OS 잠금/절전 후 복귀는 별도 항목이다. 정상 종료 시험만으로 통과 처리하지 않는다. 전경 창을 원하지 않는 동안에는 코드·빌드·백그라운드 검사만 진행하고 실기기 화면·입력 항목은 미검증으로 남긴다.

## 다중 접속과 제어권

호스트는 연결 ID마다 별도의 세션과 키보드 권한을 보관한다. 원격 커서 표시는 연결 ID를 키로 사용하고 클라이언트 이름과 색을 함께 전달한다. 이 구조가 있다는 사실만으로 다중 접속 UI와 실제 입력이 정상이라고 판단하지 않는다. Windows 호스트에 MacBook과 Android를 동시에 연결해 다음 항목을 확인해야 한다.

1. MacBook 세션을 유지한 상태에서 Android가 별도의 네트워크 경로로 로그인하고, 호스트의 연결 관리자에 두 세션이 각각 표시되는지 확인한다.
2. 두 기기에서 원격 커서 표시를 켜고 이름·색·위치가 구분되는지 확인한다. 한 세션을 종료했을 때 다른 세션의 커서와 화면 전송이 유지되어야 한다.
3. 한 세션의 키보드·마우스 권한만 끈 뒤 해당 세션은 보기와 커서 표시만 가능하고, 다른 세션의 입력은 계속되는지 확인한다. 권한을 서로 바꿔 같은 경로를 반복한다.
4. 두 세션의 30초 화면 갱신률·지연·끊김을 각각 기록하고, 단일 세션 기준과 비교한다. 연결 시작 시간이나 TLS 성공률을 화면 전송 성능으로 대신하지 않는다.
5. 각 세션을 따로 정상 종료·강제 종료·재연결하고, 남은 세션과 Windows의 로컬 화면·키보드·마우스가 계속 동작하는지 확인한다.

Windows의 실제 키보드 포커스와 시스템 커서는 하나다. 여러 접속자에게 입력 권한을 동시에 주면 입력 순서가 섞일 수 있으므로, 안정성 시험에서는 한 세션만 제어권을 갖게 한다. 제품 UI에는 접속별 `제어 중`·`보기 전용` 상태와 제어권 전환을 명확히 표시하고, 동시 입력을 정상 동작으로 간주하지 않는다.

기본 테스트는 실제 서버에 연결하지 않는다. 입력 UI 패키지의 테스트와 예제는 로컬 콜백만 사용하며 실제 원격 세션을 만들지 않는다.

```sh
cd flutter/packages/hdobby_input
flutter test
```

서버가 필요한 실기기 시험은 일반 테스트·CI에 포함하지 않는다. 실행하는 사용자가 대상 주소와 필요한 인증값을 직접 입력하고 명시적으로 연결해야 한다. 저장된 최근 연결이나 공개 서버 기본값을 시험 대상으로 자동 선택하지 않는다. 직접 연결이 불가능하면 시험을 중단하고, 사용자가 별도로 지정한 내부 중계 서버가 있을 때만 그 경로를 검토한다.

직접 TLS 경로의 연결 성공률과 시작 시간만 먼저 확인할 때는 아래 로컬 도구를 사용할 수 있다. 대상 주소·포트·인증서 SHA-256 지문을 실행자가 매번 제공해야 하며 기본 서버나 저장된 최근 연결을 읽지 않는다. 값은 출력하거나 파일에 저장하지 않는다. 이 검사는 로그인·화면·입력·클립보드 성능을 검증하지 않는다. 동시 수는 호스트의 인증 전 연결 제한을 넘지 않도록 최대 16개로 제한한다.

```sh
python3 scripts/check_direct_transport.py \
  --host '<직접 연결 주소>' --port 21118 \
  --fingerprint '<인증서 SHA-256 지문>' \
  --attempts 120 --interval-ms 1000

python3 scripts/check_direct_transport.py \
  --host '<직접 연결 주소>' --port 21118 \
  --fingerprint '<인증서 SHA-256 지문>' \
  --attempts 100 --concurrency 10 --interval-ms 200
```

실제 주소·IP·기기 ID·키·비밀번호·인증서·패킷 캡처·운영 로그·설정 백업은 Git 밖에 둔다. 이 저장소 아래 임시 보관이 불가피한 경우 무시되는 `runtime/` 또는 `secrets/`를 사용한다. 무시 규칙은 강제 추가를 막지 못하므로 커밋 전 검사와 diff 검토를 함께 수행한다. 오류 보고에도 값이나 화면 내용을 그대로 출력하지 않는다.

```sh
git config --local core.hooksPath .githooks
python3 scripts/check_private_config.py
git diff --cached
```

검사기 자체의 테스트도 임시 Git 저장소만 사용한다.

```sh
python3 -m unittest discover -s scripts/tests
```

검사기는 staged 변경만 로컬에서 읽는다. 운영 파일, 개인망 IP, 서버 설정에 하드코딩한 주소와 일부 인증값 패턴을 차단하며 의심되는 값 자체는 출력하지 않는다. 모든 형식의 비밀정보를 탐지한다고 보장하지 않으므로 수동 검토는 필요하다. 훅 설정은 clone에 자동으로 전달되지 않아 새 작업 환경에서 위 설정을 적용해야 한다.

운영 설정 예시가 필요하면 값이 빈 파일만 공유한다. 실제 내부 서버 값은 실행 시 사용자가 입력한다. 공개 서버 기본값 제거와 명시적인 내부 중계 선택 코드, 네트워크를 사용하지 않는 정책 테스트는 [네트워크 변경 설명](PRIVATE_NETWORK.md)을 따른다. 전체 앱 빌드와 실기기 검증은 아직 완료하지 않았다.

## Xcode 없는 Mac 로컬 후보 패키징

검증된 HdobbyDesk macOS Runner가 있으면 전체 Xcode 없이 로컬 시험 후보를 만들 수 있다. Dart UI를 바꾼 경우 `flutter assemble`로 만든 arm64 `App.framework`를 선택적으로 넣고, UI 변경이 없으면 생략한다. `package_macos_local.py`는 기존 앱의 번들 ID·실행 파일명·서명, 새 Flutter 프레임워크, 네이티브 코어와 서비스를 확인한 뒤 임시 개발 서명과 전체 서명 검증을 수행한다. 실제 앱을 설치·실행·덮어쓰거나 서버에 접속하지 않는다. 출력 앱과 영수증이 이미 있으면 실패하며, 둘은 미리 만든 같은 출력 폴더에 두어야 한다. 출력 폴더가 UI 앱 내부를 가리키거나 심볼릭 링크를 통해 그 안으로 들어가면 거부한다.

```sh
python3 scripts/package_macos_local.py \
  --ui-app '<검증된 기존 HdobbyDesk.app>' \
  --flutter-app-framework '<선택: flutter assemble의 App.framework>' \
  --native-core '<release liblibrustdesk.dylib>' \
  --service '<release service>' \
  --output '<새 HdobbyDesk 후보.app>' \
  --receipt '<새 로컬 영수증.json>'
```

앱 묶음 안에 운영 설정·인증서·키 파일, 앱 밖을 가리키는 링크, 깨진 링크, FIFO·소켓·기기 파일 또는 알려진 공개 RustDesk 서비스 주소가 있으면 중단한다. 구형 `librustdesk.dylib` 별칭이나 현재 `hdobby2:` 직접 페어링 프로토콜이 없는 코어도 거부한다. 영수증에는 앱 이름, 파일 수와 서명 후 네이티브·Flutter 파일 해시만 기록하며 실제 대상 주소나 인증값을 읽지 않는다. 임시 개발 서명은 공용 배포용 Apple 서명·공증이 아니다. macOS 플러그인이나 Runner를 바꾼 경우에는 전체 Xcode 빌드가 필요하다.


## Android 정적 검사

JDK 17과 기존 Gradle 7.6.4·AGP 7.3.1·Kotlin 2.1.21을 사용한다. AGP에 포함된 Lint 30.3.1은 플러그인의 Kotlin 메타데이터를 읽지 못하므로 `gradle.properties`에서 검사 도구만 8.8.2로 지정한다. [공식 Lint 가이드](https://googlesamples.github.io/android-custom-lint-rules/user-guide.html#combiningagpwithnewerlint)의 별도 버전 설정을 사용하며 검사 항목을 끄거나 기존 오류를 기준선으로 숨기지 않는다.

```sh
# 의존성을 준비한 뒤 flutter/android에서 실행. 기기 설치·연결은 하지 않음.
CARGO_NET_OFFLINE=true ./gradlew --offline :app:lintRelease -Ptarget-platform=android-arm64
```

APK 빌드 성공만으로 검사 성공을 판단하지 않는다. 전체 `lintRelease` 결과와 Kotlin 메타데이터 읽기 오류를 함께 확인한다. 2026-09-11 검사에서는 음성 통화 상태 전환 두 곳에 기존 `isSupportVoiceCall()` 조건을 적용한 뒤 오류 0개·경고 32개를 확인했다. 경고에는 저장소 권한, 서비스 참조 수명, 아이콘·리소스 항목이 남아 있다. 정적 검사는 실제 통화, 연결, 화면·입력·클립보드 시험을 대신하지 않는다.

## Android 클립보드 로컬 계측

`ClipboardInstrumentation`은 앱의 실제 Android 클립보드·이미지 디코더·FileProvider를 실행하고, 송신 콜백에서 직렬화된 메시지를 비교한다. 네트워크 전송을 실행하지 않으므로 기기 간 복사·붙여넣기 성공의 증거로 취급하지 않는다. 한글·이모지·HTML, PNG 원본 바이트, RGBA 색상, 수신 이미지의 재전송 방지, 비활성 상태, 잘못된 이미지와 크기 제한을 확인한다.

시험 앱은 `.clipboardtest` ID를 사용해 설치된 앱의 데이터와 분리한다. 일반 릴리스는 최적화 과정에서 시험 전용 Kotlin 참조를 제거할 수 있으므로 디버그 APK와 그에 맞는 시험 APK를 함께 사용한다. 시험 실행은 기본 빌드·단위 테스트에 포함하지 않는다. 실행자가 직접 선택한 빈 로컬 가상 기기를 지정한다.

```sh
# 의존성을 준비한 뒤 flutter/android에서 빌드. 연결이나 기기 설치는 하지 않음.
./gradlew --offline :app:assembleDebug :app:assembleDebugAndroidTest -Ptarget-platform=android-arm64
# 기기 설치·계측 실행은 사용자가 선택한 로컬 가상 기기의 SDK 도구에서 별도로 수행.
```

텍스트는 Unicode 문자열·줄바꿈·공백을, PNG는 SHA-256을, 다른 이미지 표현은 크기·색상·알파를 대조한다. 파일은 양쪽의 상대 경로·파일명·크기·SHA-256을 비교하고 다중 선택, 동명 파일, 취소·중단도 확인한다. 기존 파일을 덮어쓰는 테스트에는 복사본만 사용한다.

클립보드 수신은 OS/JNI로 넘기기 전에 전체 묶음을 검사한다. 표현 수는 16개, 각 표현은 압축 해제 후 64MiB, 합계는 Android 메시지 제한 80MiB에서 메타데이터 여유 128KiB를 뺀 크기까지다. 압축 해제 중에도 출력과 압축 사전 창을 제한한다. 손상·초과 입력, 잘못된 UTF-8, 양수가 아니거나 실제 바이트 수와 맞지 않는 RGBA 크기는 기존 클립보드를 변경하지 않고 거부한다. 의도적으로 보낸 정상 빈 텍스트는 허용한다. 이 제한은 파일 전송 크기를 바꾸지 않는다. PNG/SVG를 처리하는 OS 이미지 디코더의 전체 자원 사용이나 프로토콜 프레임 수신 이전의 메모리까지 검증했다고 주장하지 않는다.

관련 로컬 회귀 시험은 `cargo test --features flutter,hwcodec --lib clipboard::proto::tests --locked --offline`이다. 실제 압축 스트림의 경계·손상·연속 프레임, 전체 표현의 합계 제한, RGBA 크기, 정상 Unicode/HTML/RTF/PNG/특수 형식 보존을 확인하며 OS 클립보드나 네트워크는 조작하지 않는다. 플랫폼 간 복사·붙여넣기 시험을 대신하지 않는다.

## macOS 파일 클립보드

Mac 네이티브 코어를 직접 빌드할 때는 `flutter,hwcodec,unix-file-copy-paste` 기능을 포함한다. `build.py`의 macOS 경로는 이미 파일 클립보드 기능을 추가한다. Flutter UI나 코어 빌드 성공만으로 Finder와 다른 기기의 파일 복사·붙여넣기가 검증된 것은 아니다.

수신 파일명은 비어 있거나 절대 경로, 상위 폴더 이동, 드라이브 이름, 빈 경로 요소, 내부 NUL을 포함하면 전체 목록을 거부한다. macOS 저장은 선택한 폴더의 열린 디렉터리 핸들을 기준으로 진행하며 하위 심볼릭 링크를 따라가지 않는다. 임시 파일을 독점 생성하고, 완료 파일은 기존 항목을 대체하지 않는 방식으로 생성한다. 동명 파일에는 번호를 붙이며 취소·오류 때는 해당 작업의 미완성 파일만 제거한다. 파일 응답의 연결·번호·길이를 확인하고 빈 응답이나 요청보다 큰 응답을 거부한다.

송신은 일반 파일·폴더만 허용한다. 프로토콜의 상대 경로 제한(UTF-16 코드 단위 259개)과 목록 제한(65,536개)을 넘기거나 심볼릭 링크·특수 파일이 포함되면 오류로 처리하고 이전 파일 선택을 비운다. 파일 시간은 Windows FILETIME 기준으로 변환하며 날짜·전체 파일 크기 계산의 넘침을 검사한다.

송신 읽기 요청은 양수이고 4MiB 이하인 블록만 허용한다. 파일 위치의 상위·하위 32비트는 부호 없이 결합하므로 2GiB 경계에서도 위치를 보존한다. 남은 파일 크기를 먼저 계산해 덧셈 넘침을 피한다. 뒤에 선택한 파일이 사라져도 현재 파일에서 이미 읽은 응답을 버리지 않고, 해당 파일이 실제로 요청될 때 오류를 반환한다.

로컬 파일 시험은 아래와 같이 OS 클립보드 상태를 건드리는 별도 시험을 제외하고 실행한다. 임시 폴더에서 실제 파일 쓰기·내용 비교·동명 충돌·심볼릭 링크 거부·취소·시간 초과·캐시 교체를 검증한다.

```sh
cargo test -p clipboard --features unix-file-copy-paste --lib --locked --offline -- --skip pasteboard_context::tests::test_temp_files_count --test-threads=1
```
